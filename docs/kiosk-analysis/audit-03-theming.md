# Kiosk Theming / Design-Token Audit

Surface: `/kiosk` — `src/app/kiosk/**`, `src/components/kiosk-*.tsx`, `src/components/charts.tsx` (spot-checked, consumed by `kiosk-vitals.tsx`), against `src/app/globals.css` and `DESIGN.md` as system of record.

## Score (0-4)

**3 — good with minor hard-coding.**

Key finding: the 16-theme catalog is structurally sound — every theme fully overrides all 14 base color tokens, and the shared `.dot-*` / `Gauge` / `Meter` primitives read those tokens live via `var(--color-*)`, so status colour and charts reskin for free. But three concrete, demonstrable leaks break the "every theme, everywhere" promise: **`::selection` is hard-coded to the default teal accent and is never re-declared per `[data-kiosk-theme]`**, so every one of the 15 non-default themes shows the wrong selection-highlight colour; the **hatch pattern (`HATCH_PATTERN`) hard-codes a literal that happens to equal `--color-ink-faint`'s *default* value**, so "unconfigured" placeholder textures freeze to the dark theme's tint on every theme; and `color` — like `font-family` before it — is set once on `body` outside the scope and only *inherited*, the same bug class the code already had to fix once for fonts, now latent for any un-classed text node.

## Theme × variable matrix (holes marked)

All 16 themes (default + 15) redeclare the full 14-token color set (`bg, panel, panel-2, line, line-bright, ink, ink-dim, ink-faint, accent, accent-dim, blue, ok, warn, bad`) inside their `[data-kiosk-theme]` block in `globals.css:345-803`. **No color-token holes** — every theme that omits a variable would silently inherit the dark default, and none do. That is the one thing this catalog gets fully right.

Font tokens are a different story — `--font-sans` is **not** overridden by 5 of the 15 themes, silently falling back to Inter:

## Findings

**P1 — `::selection` is not theme-scoped.** `globals.css:64-66` hard-codes teal (`rgba(94,234,212,0.25)`) globally with no `[data-kiosk-theme] ::selection` override anywhere in the 459 lines of kiosk theme CSS. Every non-default kiosk theme shows the wrong selection colour. Trivial to reproduce: select any text on `/kiosk?theme=neon`.

**P1 — `HATCH_PATTERN` hard-codes what is actually `--color-ink-faint`, and ignores theme entirely.** `kiosk-display.tsx:48` and `kiosk-hub.tsx:56` (identical literal, duplicated across two files instead of a shared constant) bake in `rgba(77,97,122,0.14)`, the *default* theme's ink-faint at 14%. `WeatherUnconfigured`, `HubUnconfigured`, and `HubEmpty` all render this hatch texture — on every one of the 16 themes, it renders in the same dark blue-gray, never the active theme's own ink-faint. Should be `color-mix(in srgb, var(--color-ink-faint) 14%, transparent)`, matching the pattern DESIGN.md itself prescribes and that `.log-arrival`/`.rail-arrival` already use correctly for accent washes (`globals.css:227,246`).

**P1 — DESIGN.md's `rounded.tile: 0.5rem` token was never wired into Tailwind, and the one place that needed it wrote the literal instead of `rounded-lg`.** `DESIGN.md:100` documents `tile: "0.5rem" # kiosk touch tiles (56px+)` in its `rounded` token block, but `globals.css`'s `@theme` block declares **no `--radius-*` custom properties at all** (confirmed: zero matches for `--radius` in the file) — the whole radius scale, "tile" included, is pure narrative documentation riding on Tailwind's *coincidental* default `lg = 0.5rem`. Every kiosk touch tile (`kiosk-hub.tsx` `ToggleTile`/`SceneTile`, `kiosk-glance.tsx`'s tile buttons) correctly uses `rounded-lg` and gets 0.5rem by luck of Tailwind's default scale never having been overridden. `kiosk-timers.tsx:436` is the one place that didn't get the memo — it hand-writes `rounded-[0.5rem]` instead of `rounded-lg`, the literal-vs-utility drift the "tile" token was supposed to prevent by existing. If Tailwind's default `lg` radius ever changes, or a real `--radius-tile` token is added later, this line silently stops matching every other tile on the surface.

**P1 — latent theme-scope leak on `color`, same class as the fixed `font-family` bug.** `globals.css:37-40` sets `body { color: var(--color-ink); font-family: var(--font-sans); ...}`. The kiosk theme div (`[data-kiosk-theme]`, `globals.css:60-62`) re-declares `font-family: var(--font-sans)` specifically because — per the file's own comment — "`body`'s value is computed once, OUTSIDE the scope, and merely inherited," so a themed `--font-sans` override never reaches descendants without the re-declaration. **The identical mechanism applies to `color`**, and `color` is *not* re-declared anywhere in `[data-kiosk-theme]`, nor is `text-ink`/equivalent applied to the `KioskThemeScope` div itself (`kiosk-theme.tsx:217`: `className={cn("min-h-screen bg-bg overflow-x-hidden", ...)}` — no color utility). In this codebase every text-bearing leaf I read happens to carry an explicit `text-ink`/`text-ink-dim`/`text-ink-faint` Tailwind class, which re-resolves `var(--color-ink)` locally and sidesteps the bug — but that is incidental code discipline, not a structural guarantee, and it is exactly the kind of thing the font-family bug (found "live by all three theme-QA agents independently") slipped through on. Recommend adding `color: var(--color-ink);` next to the existing `font-family` line in `[data-kiosk-theme]` as defense-in-depth.

**P2 — `LIGHT_THEMES` in `kiosk-sky.tsx:50-60` is a third independent restatement of "which themes are light."** The set of 9 theme names (journal, folio, slate, sunroom, aerogel, bulletin, understory, duotone, cinderblock) is currently in perfect sync with the 9 `color-scheme: light` declarations in `globals.css`, but nothing enforces that — a new light theme added to the catalog without updating this list would get the wrong (0.10, dark-theme) ambient sky opacity cap instead of the intended 0.05, muddying its ground. This is the same shape of risk `KIOSK_THEME_SWATCHES` already accepts knowingly (with a comment); this second duplication has no such comment or warning.

**P2 — `active:scale-[0.97]` vs `active:scale-[0.98]` is drift, not a decision.** 16 of 17 press-scale sites use `0.98`; `kiosk-glance.tsx:129` alone uses `0.97`. DESIGN.md itself calls out this exact failure mode in its own typography section ("a new value within 0.02rem of an existing step is drift, not a decision") — the same logic applies here.

**P2 — Chrome theme's mono font is borrowed from Aerogel with no token of its own.** `globals.css:737`: `--font-mono: var(--font-t-aerogel-mono), ui-monospace, monospace;` inside `[data-kiosk-theme="chrome"]`. No `fChromeMono` font const exists in `kiosk-theme.tsx`. Functionally harmless today, but an implicit cross-theme dependency that isn't documented anywhere near the Chrome block's own comment (`globals.css:719-720`), unlike every other reuse in this file which is either the shared default or explicitly commented.

**P2 — DESIGN.md's dark-only commitment isn't annotated as kiosk-exempt in the doc itself.** DESIGN.md's own Don'ts (`DESIGN.md:435`) state: *"Don't add a light theme, a theme toggle, or a `prefers-color-scheme` branch. This world is dark only."* The kiosk ships 9 light-ground themes. The code comments in `globals.css:338-340` correctly scope the exception ("The dashboard proper stays dark-console-only (DESIGN.md brand commitment); the wall display is the one surface allowed to dress up") — but DESIGN.md, which is supposed to be the system of record per this audit's own brief, contains no such carve-out anywhere in its text. Anyone auditing DESIGN.md alone (without reading `globals.css` comments) would flag every kiosk light theme as a hard violation of a documented Don't.

**P3 — `text-[0.6rem]` (`kiosk-display.tsx:425`) is a single-occurrence size that matches neither the Tick (`0.5rem`) nor Detail (`0.65rem`) documented steps.** Low blast radius (one rain-percentage caption), but exactly the kind of undocumented in-between value DESIGN.md's own Bottom-Heavy Ramp Rule warns against.

## Already correct

- **Every theme fully overrides all 14 base color tokens** — no theme silently inherits a stray dark-mode color, which was the single failure mode the audit brief specifically asked to hunt for. This is the hard part and it's done right across all 15 themes.
- **Status dots, `Gauge`, and `Meter` are fully theme-reactive with zero kiosk-specific code.** `.dot-running/.dot-unhealthy/.dot-restarting/.dot-stopped/.dot-dead` (`globals.css:90-118`) and `charts.tsx`'s `Gauge`/`Meter` (confirmed via `stroke="var(--color-accent)"` etc., `charts.tsx:10,66,91,95`) consume `var(--color-*)` directly, so `KioskHub`, `KioskHealth`, `KioskStatusStrip`, and `KioskVitals` all reskin for free with no per-theme special-casing needed anywhere in those five components.
- **Semantic color discipline holds.** Zero uses of `text-ok`/`bg-ok`/`border-ok` anywhere in the kiosk surface (confirmed by grep) — `ok` green is never reached for decoratively; every `ok`/`warn`/`bad` usage found during this audit traces to a real state (container health, timer finished, PIN error, temperature threshold). Accent is reserved for live/selected/primary-action state (`dot-live`, active tabs, primary buttons) and never used as ornament.
- **`KIOSK_THEME_SWATCHES`' literal-hex duplication is the one case of intentional, well-documented duplication** — the comment explicitly explains why (CSS vars can't cross scope boundaries for a picker preview) and instructs future editors to keep it in sync. This is the right way to accept an unavoidable literal; contrast with the undocumented `HATCH_PATTERN`/`::selection`/`LIGHT_THEMES` duplications above.
- **Rain/timer SVG chart elements consume theme vars correctly** — `stroke="var(--color-line-bright)"` / `fill="var(--color-blue)"` in `kiosk-display.tsx:491,507`, `stroke="var(--color-line)"` / `stroke={warn ? "var(--color-warn)" : "var(--color-accent)"}` in `kiosk-timers.tsx:336,342` — no hand-rolled chart in the kiosk surface hard-codes a color.
- **`--text-2xs` (the already-promoted 0.7rem token) is used correctly and consistently** everywhere a `0.7rem` mono caption appears (`kiosk-hub.tsx`, `kiosk-status-strip.tsx`, `kiosk-admin-panel.tsx`, `kiosk-display.tsx`'s `ForecastStrip`) — no remaining `text-[0.7rem]` literal duplicates it anywhere in the kiosk surface.
- **Motion is reduced-motion-safe everywhere it touches the kiosk** (`kiosk-pin-shake`, `voice-mic-recording`, `net`-adjacent rules N/A here) — not a theming concern per se, but confirms the surface follows DESIGN.md's Do's consistently outside of color too.
